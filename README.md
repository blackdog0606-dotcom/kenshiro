# Kenshiro 黒枠自動クロップ・最小版

**[v0.1.4 黒帯検出修正版ZIPをダウンロード](https://github.com/blackdog0606-dotcom/kenshiro/raw/refs/heads/main/downloads/kenshiro-blackcrop-mvp-0.1.4.zip)**（テスト用TIF10枚付き）。解凍後、UXP Developer Tool の **Add Plugin** で `kenshiro-blackcrop-mvp-0.1.4/manifest.json` を指定してください。

「画像端から連続する黒帯のみ」では、最外周に白い余白がある画像の内側の黒枠へ到達できず、四辺とも0pxになっていました。v0.1.4では選択肢を **「画像端の黒帯（白い余白内の枠にも対応）」** に改め、画像端の黒帯が四辺とも0pxの場合だけ、既存の四辺コマ枠検出を続けて行います。四辺を確認できた枠の内縁までをCrop値にし、各結果に実際に使った検出方法を表示します。四辺枠も確定できない場合はスキップし、0%で既存Cropを上書きしません。黒判定・95%判定・0.1%への丸めは維持しています。

初期設定の **「白い余白＋黒いコマ枠」** の検出処理は変更していません。別途調査中の枠内縁の修正は、この版には含めていません。**Cropの四辺だけを変更し、拡大や位置調整は行いません。**

Premiere Pro 26.5.2では、v0.1.3の標準Crop追加と値の適用が実機診断で確認されています。標準Cropの内部名 **`AE.ADBE AECrop`** の識別を引き続き使います。今回の検出修正はクラウドでテストしており、v0.1.4の実機結果は未確認です。

### 旧版からの更新と診断

1. UXP Developer Toolで旧版を **Unload** し、**Remove** で登録を解除します。
2. 新しいZIPを解凍し、**Add Plugin** で新しいフォルダー内の `manifest.json` を指定して **Load** します。
3. パネルの見出しが **黒枠自動クロップ v0.1.4**、その下が **起動済み v0.1.4** になっていることを確認します。「起動・実行エラー」が出た場合は、その文章を報告してください。ボタンは処理登録が完了するまで無効になっています。
4. 静止画1枚を選択し、今回の修正を試す場合は **画像端の黒帯（白い余白内の枠にも対応）** にして、**①解析→②適用** します。結果に出る検出方法と四辺の値を確認してください。
5. 失敗したら、件数の直下に出る **失敗理由** と、その下の **診断情報** 欄の文章をコピーして報告してください。診断欄をクリックして Ctrl+A（MacはCmd+A）で選択し、コピーできます。

診断情報は選択中の先頭ビデオクリップについて、利用可能なCrop名・エフェクト名・パラメータ名・値の型と数値／真偽値を読み取ります。診断ボタン単独ではエフェクトを変更しません。素材パス、プロジェクト名、任意のテキスト値は収集せず、自動送信もしません。

起動スクリプトはAPP LOGSに `[Kenshiro] bootstrap v0.1.4`、ボタン登録後は `[Kenshiro] panel handlers ready v0.1.4` を出力します。ボタンを押すと `[Kenshiro] 解析 click` などが記録されます。AdobeのDiscover Panelのログとは区別して確認できます。変更を伴う適用処理自体は、遅れて変更が発生する危険を避けるためタイムアウトで放置しません。

Premiere Pro **25.6以降**用のUXPパネルです。タイムラインで選択した静止画を元画像から解析し、標準 **Crop（クロップ）** の Left / Right / Top / Bottom を一括設定します。**白い余白＋内側の黒いコマ枠を除去するモード**を初期設定にしています。画像端の黒帯を優先し、黒帯がなければ白余白内の四辺枠を確認するモードも選べます。既存プラグインのコードが未登録のため、単体プラグインとして作成しています。

## 導入

開発時はNode.js 22以降を使用します。クラウドではNode.js 24で検証しています。

```sh
cd /workspace/kenshiro
npm ci
npm run check
npm run samples
npm run samples:tiff
npm run samples:panels
```

ローカルPCにリポジトリをコピーした場合は、そのフォルダーで同じコマンドを実行してください。`npm run build` が `dist/main.js` を生成します。依存ライブラリはすべてバンドルされ、Premiere側でNode.jsを起動する必要はありません。

1. Premiere Proを起動し、環境設定のプラグイン設定で開発者モードを有効にします。
2. Adobe UXP Developer Toolで **Add Plugin** を選び、このフォルダー直下の `manifest.json` を指定します。
3. **Load** を実行し、Premiereのプラグインメニューから「黒枠自動クロップ」を開きます。

ビルド済みZIPを使用する場合は解凍したフォルダーの `manifest.json` を指定します。開発用の未署名パッケージで、Marketplace版や署名済みCCXではありません。

元画像をパスから直接読むため `localFileSystem: fullAccess` を要求します。画像の書き換え・アップロード・ネットワーク通信は行いません。

## 10枚で試す

1. `npm run samples:panels` で生成した **`test-panels/` のTIF10枚**をPremiereへ**個別の静止画として**読み込みます。「画像シーケンス」はオフにしてください。
2. テスト用シーケンスへ並べます。実素材を試す場合はシーケンスを複製してください。
3. タイムラインで静止画クリップを最大10件選択し、検出モード「白い余白＋黒いコマ枠」のまま「①解析」を押します。
4. ピクセル数と0.1%単位のCrop値を確認して「②適用」を押します。
5. **最初は1枚だけ**適用し、エフェクトコントロールのCrop四辺の表示百分率が解析結果と一致するか確認してから10枚処理してください。APIの読み戻し検証は保存数値の一致を確認しますが、実機UIの単位表示まではこのクラウドで検証できません。下のトラックに赤や黄色のカラーマットを置くと、クロップ後の境界を確認しやすくなります。
6. 同じフォルダーの `expected.json` と比較します。枠なし・三辺だけの枠はスキップが正解です。各ファイルの期待値はJSONで確認できます。
7. 再解析・再適用し、Cropが重複追加されないことを確認します。クリップを1件だけ選択するケースも試してください。

既存Cropの四辺は上書きします。既存Cropが複数、四辺にキーフレームあり、Zoom有効、ぼかし有効の場合は変更せず理由を表示します。日本語・英語の標準パラメータ名を識別し、未知の名前をインデックスで推測して変更しません。

変更はPremiereのUndoに登録します。**既存Cropの更新は1クリップ1回、新規Cropは追加と値設定の2回**のトランザクションです。一括処理全体が1回のUndoになるわけではありません。失敗時は、追加したCropの削除または既存値の復元を試み、復元失敗も画面へ表示します。

画像端の黒帯は、検出モードを「画像端の黒帯（白い余白内の枠にも対応）」へ切り替え、`npm run samples` の `test-images/`（PNG10枚）または `npm run samples:tiff` の `test-images-tiff/`（TIF10枚）で試せます。このセットでは1枚目の枠なし画像と10枚目の全黒画像をスキップします。枠なし画像の検出値は0ですが、アプリは0%の適用を行いません。

「中断」は処理中の1件が終わってから次のクリップへ進む前に停止します。すでに適用した分は残ります。選択・シーケンス・元画像を変更したら再解析してください。適用ボタンは**解析したクリップ**を対象にします。

## 判定仕様

両モードとも黒の定義は **R ≤ 20、G ≤ 20、B ≤ 20**、Crop値は元画像サイズに対する百分率を小数点以下1桁へ四捨五入します。アルファは判定に使いません。

### 白い余白＋黒いコマ枠（初期設定）

白い余白の内側にある四辺の長い黒線から、長方形のコマ枠を探します。確認できた枠の**内縁**まで切り取るため、Cropピクセル数には外側の白い余白と黒線の太さの両方が含まれます。

スキャンのわずかな傾き・線の揺れには細い帯の投影で対応します。帯の中に黒画素がある位置を数え、枠の一辺の長さに対して95%以上の被覆を要求します。帯幅は各寸法の3%以内（最低2px）に制限します。このモードの95%は**候補の枠に沿った帯の被覆率**で、元の黒帯モードの「画像全幅・全高に対する1行・1列の黒率」とは別の判定です。

四辺がそろわない、太すぎる・傾きが大きい・複数の枠などで一意に確定できない場合はスキップします。描画の外接矩形だけを求めて顔や効果線を自動的に切り捨てる処理はしません。四角い描画をコマ枠として誤認する可能性はあるため、少数ずつ試し、適用後に実画面を確認してください。

### 画像端の黒帯（白い余白内の枠にも対応）

1. 各行は元画像の全幅、各列は元画像の全高で黒率を測り、**95%以上**を黒帯とします。四辺それぞれ外周から走査し、最初の条件不成立行・列で止めます。
2. 1辺以上の黒帯を検出した場合は、その検出値をそのまま使います。ほかの辺の内側にある枠は追加探索しません。
3. 正常な検出結果で四辺とも0pxの場合だけ、上記の既存コマ枠検出を試します。四辺の枠を95%以上の帯の被覆率で確認できた場合に、白余白と黒枠を含めて内縁までクロップします。コマ枠の95%は帯の被覆率で、黒帯の全幅・全高に対する黒率とは異なります。
4. 四辺枠も確定できない場合は、理由を表示してスキップします。全黒や、百分率の丸めで内容が消える場合もスキップし、コマ枠検出で置き換えません。

Left / Right は `枠px ÷ 元画像幅 × 100`、Top / Bottom は `枠px ÷ 元画像高 × 100` を四捨五入して小数点以下1桁へ変換します。JPEGも縮小せず元解像度で解析し、デコード後のRGBに同じ閾値を適用します。結果欄には、画像端の黒帯と白余白内の四辺枠のどちらを使ったかを表示します。

95%という条件上、画像の大部分が黒で小さな絵だけある画像や、端まで接している黒い描画も枠として認識される場合があります。解析値を確認してから適用してください。0.1%への四捨五入により、検出した境界と最大0.05%相当の差が生じます。

## Cropだけを変更します

**Motionのスケール・位置・回転・アンカーポイントは変更しません。** 自動拡大、画面を埋める位置調整、拡大の目安表示も行いません。クロップ後も、選択したクリップの元の大きさと位置を保ちます。

## 対応範囲と検証状況

- PNG、JPEG、通常の単一ページTIFF（`.tif` / `.tiff`）。TIFFは8bitグレースケール・RGB/RGBA、ストリップ形式、LZW／PackBits／無圧縮、Predictor 1/2に対応します。CMYK、16bit、パレット、タイル、チャンネル分離、Deflateなどは変換が必要です。
- 最大4,000万画素、各辺20,000px、ファイル100MBまで。逐次処理で画像を解放しながら進めます。
- 動画、画像シーケンス、ネスト、オフライン素材、APNG、BigTIFF、複数ページTIFF、回転・反転の向き情報を持つ画像は対象外です。画像編集ソフトで向きを確定して単一静止画として保存してください。
- UXP APIには画像シーケンス専用判定がないため、拡張子だけでは完全に除外できません。**個別静止画として読み込んだクリップだけ選択してください。**
- PSD、HEIC、カラーマネジメント後のプログラムモニター画面、適用済みエフェクトの出力は解析しません。解析対象は元画像のデコードRGBです。
- ネットワーク共有のUNCパスは最小版の対象外です。ローカルへコピーして再リンクしてください。
- Linuxクラウドではデコーダー・検出・丸め・生成画像・ホストAPIモック・バンドル生成を検証しています。Premiere Pro 26.5.2ではv0.1.3のロードと標準Crop適用が確認済みです。v0.1.4の検出修正はクラウドでの検証であり、実機での修正結果は未確認です。
- v0.1.4は176件の自動テストが成功しました。白余白付き横長TIFF、従来の黒帯検出、RGB20・95%の境界、枠なしのスキップ、Motion値の維持を含みます。

Adobeの公式UXP APIに沿って選択取得、エフェクト追加、値更新、読み戻しを実装しています。個別エフェクトの名前・値形式は実機差があり得るため、未知の構成はエラーにして変更を止めます。

提供された `25-142-4.tif` は3331×1702px・8bitグレースケール・LZW・Predictor 2・向き1でした。実際にデコードし、Pillowによる独立したRGBA変換とSHA-256が一致しました。既存コマ枠検出は白余白＋枠を含めて左38px・右50px・上42px・下43pxを検出し、**Left 1.1% / Right 1.5% / Top 2.5% / Bottom 2.5%** に丸めます。厳密な画像端走査だけでは最外周が白いため四辺0pxですが、v0.1.4の黒帯モードは続けて四辺枠を確認し、同じ百分率を返します。

今回追加で共有された3631×1815pxの画像は、チャット上の縮小画像だけを受領しており、元TIFのピクセルデータは未取得です。この画像の正確な検出値は確認していません。似た横長の構成を持つ生成画像と、上記の既存の元TIFで検出経路を検証しています。ユーザー提供の画像は生成テスト画像や配布ZIPに同梱しません。
